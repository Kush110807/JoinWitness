# 01 | EXECUTIVE DIRECTIVE — WHAT WE ARE BUILDING

### Decision

Build **JoinWitness**, an accessible AI-assisted *conclusion-robustness auditor* for two imperfectly matching datasets. It must answer a materially different question from conventional entity resolution:

**“Given the identity links that a reviewer considers permissible, could a different valid linkage change my analytical conclusion? If so, show the smallest verified change; if not, explain the conditional boundary of that statement.”**

The flagship story is event registration vs actual attendance. Three check-in records are linked against four registrations with Group A/B labels. The reference assignment says Group A leads, **2 to 1**. One ambiguous “Kim/Kym” record can legitimately refer to Group B instead. With that single changed assignment, Group B leads, **2 to 1**. The resulting witness is independently checked; on the tiny fixture, independent exhaustive enumeration confirms that **one** is the minimum number of changed attendance assignments.

**Product promise:** *Find out whether uncertain matches can change the answer — before you act on that answer.*

**One-line pitch:** *Meta AI proposes plausible matches. JoinWitness tests the conclusion across allowed alternatives and produces independently replayable evidence.*

This is not another fuzzy CSV merger, generic LLM chat app, identity oracle, enterprise MDM suite, or Apple integration. It is a single exceptionally clear, technically defensible demonstration.

### Product priorities, in order

1. An **honest, fully working end-to-end demonstration** with correct mathematics.
2. **Genuine Meta Model API integration** that creates measurable user value, not decorative AI.
3. An **independent checker and exact oracle** for flagship and small adversarial examples.
4. A **calm, beautiful, immediately comprehensible interface** with visible user control.
5. A reproducible repository, robust deployment, evidence bundle, and coherent demo video.

A feature may be cut to protect those five priorities. A correctness guard, trust boundary, or evidence requirement may **not** be cut to obtain a prettier screen.

# 03 | CUSTOMER AND THE ONE STORY WE WILL PROVE

**Who has this problem?** Event operators, small research teams, university administrators, volunteer coordinators, aid programs, analytics teams, and auditors who reconcile names or records from two sources and then make a decision from the joined output.

**What is wrong with today's common workflow?** A conventional process typically picks one best match, calculates a metric, and presents a conclusion. Confidence in each individual match does **not** directly answer whether match uncertainty changes the decision. One low-confidence record might be irrelevant, while another could reverse a decision.

**JoinWitness's unique wedge:** *decision-aware sensitivity* under explicit constraints. We must not claim we invented constrained entity resolution or mathematical programming. We should demonstrate the useful synthesis: model-assisted candidate interpretation, human-reviewed admissible alternatives, exact reversal search, a changed-assignment witness, and independent receipt replay.

### Frozen flagship synthetic fixture

**registrations.csv**

| registration_id | name | group |
|---|---|---|
| R-A1 | Amara Shah | A |
| R-A2 | Kim Rao | A |
| R-B1 | Bryn Ellis | B |
| R-B2 | Kym Rao | B |

**attendance.csv**

| attendance_id | recorded_name |
|---|---|
| T-01 | Amara Shah |
| T-02 | Kim/Kym Rao |
| T-03 | Bryn Ellis |

**Reviewed policy**: T-01→R-A1 CONFIRMED; T-03→R-B1 CONFIRMED; T-02→R-A2 POSSIBLE; T-02→R-B2 POSSIBLE; unmatched for T-02 forbidden **only because the reviewer explicitly forbids it for this synthetic fixture**. Every other edge is either expressly prohibited or excluded by the declared, limited review universe. No omitted link is silently treated as disproven real-world identity.

**Baseline/reference**: T-01→R-A1, T-02→R-A2, T-03→R-B1. Group A=2, B=1. Predicate `A > B` is TRUE.

**Checked alternative**: T-01→R-A1, T-02→R-B2, T-03→R-B1. Group A=1, B=2. Predicate is FALSE. Exactly one attendance assignment changed, so changed-assignment distance=1.

**User-facing sentence**: *“One unresolved identity match can reverse your conclusion. Verify T-02 before acting.”* The second sentence is a suggested human review action, not an assertion that we know the real identity.

### Additional mandatory narratives

- **Stable within policy**: no permitted matching reverses the predicate; explicitly note the result depends on coverage/policy.
- **Two changes needed**: create a fixture with optimum changed-assignment distance 2; exhaustive oracle must show no one-change reversal.
- **Inconclusive**: time limit, source revision, or model failure never becomes a definitive stable result.
- **Coverage incomplete**: a mathematically stable conclusion in a narrow candidate universe must not be advertised as real-world certainty.

### Information architecture: four stages, not a sprawling dashboard

**I. Import** — “What are we comparing?”

- Exact preview with validation. Reject duplicate primary IDs and malformed groups. Optional synthetically preloaded *Try the demo* action.

**II. Review** — “Which matches are legitimately possible?”

**III. Challenge** — “Could the result change?”
- Explicit fixed question: “Did Group A have more attendance records than Group B?”

- View changed rows, allowed-edge reasons, full assignments, proof-status attribution, checker checklist and coverage caveats.
- Download receipt and replay command. Clearly differentiate **witness validation**, **solver-proved optimality**, and **solver-proved lack of a reversal**.
- Always show “What this does not establish: the true identities or complete universe of all possible matches.”

### Core visual hierarchy

1. Headline verdict and comparison before/after counts.
2. Changed record(s) and exactly why each alternative is allowed.
3. Evidence and reviewer policy.
4. Technical status, hashes, and reproducibility details one level deeper.

**Avoid:** fake activity graphs, progress percentages not measured, untrusted “99% confidence” badges, auto-green “safe” labels, unnecessary animated particles, AI-generated prose standing in for an actual checker, or apple-branded design elements.

# 06 | TRUST, AUTHORITY AND PERMISSION MODEL

The permitted flow is:

```text
CSV bytes → validated row IDs/fields → deterministic candidate shortlist
          → Meta AI suggestions [UNTRUSTED]
          → explicit human review [AUTHORITATIVE FOR MODEL]
          → frozen reviewed universe + baseline + question [IMMUTABLE SNAPSHOT]
          → CP-SAT reversal search [MATHEMATICAL STATUS]
          → independent witness checker + small exact oracle [VERIFICATION]
          → typed result + honest UI + replayable receipt
```

1. **CSV source authority**: original source bytes are immutable during a run; record row order and digest. Registration group labels are factual inputs as supplied, **not** corrected by the AI.
2. **Model authority**: Muse may rank, annotate, or propose existing candidate IDs, nothing more. JSON structure is not semantic truth.
3. **Reviewer authority**: only explicit human action authorizes an edge to be confirmed or possible. An edge never becomes confirmed because of a high AI score.
4. **Universe authority**: uncertainty is defined by *reviewed permitted candidate edges*, explicit unmatched choices, and explicit coverage qualification. Unreviewed/missing edges are not silently assumed to be impossible in reality.
5. **Baseline authority**: a full valid reference assignment tied to immutable policy digest is required; never choose a convenient baseline merely to make the demo reverse.
6. **Solver authority**: may report feasibility, optimum, infeasibility **for its exact model**, not identity truth.
7. **Checker authority**: separately recomputes validity and counts of a proposed witness. Checking a witness does **not** establish its global minimum unless a separate oracle or solver completion supports that claim.
8. **Snapshot freshness**: any edit to input data, group labels, review permissions, unmatched policy, or baseline invalidates earlier results until rerun.
9. **No secret authority bypass**: model output, browser UI state, cached demo response, or GitHub README cannot change the saved reviewed policy.

**Coverage labels:** `UNREVIEWED`, `REVIEWED_PARTIAL`, `REVIEWED_CLOSED_SCOPE`. Even `REVIEWED_CLOSED_SCOPE` expresses a scope agreed for this analysis, not a guarantee that every real-world identity candidate has been discovered. Always display the exact review scope.

# 07 | MATHEMATICAL CONTRACT — NOT NEGOTIABLE

Let attendance rows `i ∈ I` and registrations `j ∈ J`, each registration with a fixed group label `g(j) ∈ {A,B}`. Let `P_i ⊆ J` denote explicitly permitted registration choices, and `U_i ∈ {0,1}` indicate explicit permission for unmatched `⊥`.

### Variables

`x[i,j] ∈ {0,1}` for admitted edges `j ∈ P_i`. `x[i,⊥] ∈ {0,1}` only if unmatched is permitted.

### Feasibility constraints

```text
For every attendance row i:
    sum(x[i,j] for j in P_i) + x[i,⊥] = 1
    (x[i,⊥] is fixed to 0 if unmatched forbidden)
For every registration j:
    sum(x[i,j] for all i admitting j) ≤ 1
For each CONFIRMED i→j:
    x[i,j] = 1
For each REQUIRED unmatched i:
    x[i,⊥] = 1
For PROHIBITED or unreviewed edges:
    no permitted decision variable exists
```

Reject contradictory confirmations, conflicts over the same registration, unsatisfiable basic policies, and unallowed unmatched choices. Do not silently resolve conflicts or guess identities.

### Decision predicate and reference

```text
A(x) = sum(x[i,j] for g(j) == A)
B(x) = sum(x[i,j] for g(j) == B)
T(x) = (A(x) > B(x))
T0   = T(reference)
D(x, reference) = sum(1 for each i if assignment_x(i) != assignment_ref(i))
```

A tie makes `A>B` **false**. Every observed attendance row is one unit; the application must not represent duplicate physical attendances as deduplicated persons unless that has separately been established. An unmatched attendance row counts in neither group.

**Reverse-target search:** If `T0` is true, constrain `A(x)−B(x) ≤ 0`. If `T0` is false, constrain `A(x)−B(x) ≥ 1`. Minimize `D(x,reference)`.

### Solver status interpretation (OR-Tools CP-SAT)

| Solver observation | Additional checks | Legal result |
|---|---|---|
| `OPTIMAL`, alternative exists | Independent checker accepts witness, count flip and distance | `REVERSIBLE_MINIMUM_PROVEN` (minimum certified by complete solver optimization; oracle cross-check on small instances) |
| `FEASIBLE`, alternative exists, not optimum | Independent checker accepts | `REVERSIBLE_WITNESS_ONLY` |
| `INFEASIBLE` under reverse constraints | Exact model and snapshot validated; where small, independent oracle agrees | `STABLE_WITHIN_REVIEWED_POLICY` |
| `UNKNOWN`, timeout, crash, model invalid | No checked alternative | `NOT_VERIFIED` |
| Any status with failing checker | Treat as correctness failure; block release | `NOT_VERIFIED` and investigation |

If the solver reports `FEASIBLE` and the checker rejects the witness, **do not** display reversal. If `OPTIMAL` and the checker rejects the candidate, **do not** advertise optimality. A separate exact small-instance oracle must independently enumerate admissible assignments and verify true/false outcome and minimum distance; the checker alone cannot prove nonexistence or global optimality. Production-sized solver status remains solver-attributed, not independently formally proved by the checker.

**Determinism:** freeze model inputs and hashes; pin OR-Tools version; log seed, parameters and time limit. Accept that optimized runtimes may vary; reproduce logically equivalent results, not necessarily identical solver traces.

**Implementation prohibition:** never use an LLM's arithmetic, natural-language assurance, or confidence estimate as the certificate that no reversal exists.

# 08 | VERSIONED DATA CONTRACTS AND RECEIPTS

Use Python 3.11+, Pydantic models, stable serialization and schema-version IDs. The coordinator must approve exact fields before implementation. Preferred entities:

- `Registration`: `registration_id`, `display_name`, `group`, optional approved comparison fields.
- `Attendance`: `attendance_id`, `recorded_name`, optional approved comparison fields.
- `CandidateSuggestion`: both existing IDs, provider/model, prompt/schema version, model request ID, visible-field evidence references, bounded rationale, triage priority, **not permission**.
- `ReviewedEdge`: IDs, `CONFIRMED | POSSIBLE | PROHIBITED`, review operation, optional evidence reference, revision.
- `UnmatchedPolicy`: per attendance `ALLOWED | REQUIRED | FORBIDDEN`.
- `ReviewSnapshot`: exact input-byte and normalized-record digests, admitted edge set, relevant explicit prohibition record, unmatched policy, scope/coverage, revision, sorted canonical JSON SHA-256.
- `ReferenceMatching`: complete row→registration-or-unmatched choices, frozen review digest.
- `DecisionQuestion`: fixed type `A_COUNT_GREATER_THAN_B_COUNT`, version, group field.
- `AnalysisResult`: typed status, solver status/version/limits, complete/partial indicators, baseline/witness assignments and counts, changed rows, verifier verdict, caveats, references, timestamps.
- `VerificationReceipt`: portable versioned JSON binding all above content digests, checker result, provenance of AI claims, and replay contract.

### Required receipt properties

- Hash raw source data and a documented stable parsed ordering; do not silently canonically sort rows in one component while another assumes original order.
- Make every assignment **ID-based**, never position-only or displayed-name based.
- Fail closed on unknown fields that could affect authority; allow explicitly versioned extension fields only under a documented policy.
- Separate model event metadata from reviewer decisions and solver results.
- Plain SHA-256 is an integrity fingerprint, **not a cryptographic signature** if an attacker can replace both content and hash. Avoid “tamper-proof” claims.
- Version every snapshot and invalidate on edit. Don't let UI state mutate a frozen analytical result.

**Target replay command** (a design contract, not a claim that the command already works):

```bash
python -m joinwitness.verify \
  --receipt results/demo_receipt.json \
  --registrations fixtures/demo/registrations.csv \
  --attendance fixtures/demo/attendance.csv \
  --policy results/review_snapshot.json
```

The command must recompute source hashes, admissibility, one-to-one uniqueness, counts, baseline status, alternative status and changed-distance. Global optimality and infeasibility are attributed to solver completion and, on tiny cases, independently checked by the exhaustive oracle.

# 09 | THE META INTELLIGENCE LAYER — USEFUL BUT UNTRUSTED

### What Meta AI must actually do in the live app

1. Validate CSVs locally and produce a deterministic candidate shortlist using normalized text and selected fields.
2. Send an approved, minimized synthetic/consented batch to **Meta Muse Spark 1.3** in **Standard mode**.
3. Ask for schema-constrained JSON containing **only supplied IDs**, candidate ordering, observed supporting fields and concise ambiguity explanations. Never ask the model to invent identities, derive A/B counts or determine the verdict.
4. Strictly validate all returned IDs, enums, arrays, lengths and evidence references against the original rows; reject fabricated IDs and unsupported properties.
5. Present suggestions as **unreviewed** and make the human explicitly authorize possible/confirmed links. Empty AI responses and partial failures must be safely handled.
6. Log model ID, prompt version, schema version, request ID (if available), token usage, latency and errors. Never log raw private data or keys into a public artifact.
7. For the flagship, capture one **actual live Meta call** and its redacted evidence, and demonstrate the deterministic fallback when the model is unavailable.

### Why Meta is essential to the user experience

The AI is valuable if it helps a human find and understand plausible aliases in messy records, reduces review burden, or asks a focused clarification question about a **verified decision-critical ambiguous row**. That value needs evidence, not a slideshow statement. Make the project **AI-assisted with deterministic authority**, not an AI chatbot whose guesses are treated as mathematics.

### Controlled evaluation / ablation

Run the same frozen synthetic cases for (A) deterministic shortlist only and (B) deterministic shortlist plus Muse suggestions. Measure candidate recall@k against **known synthetic truth**, hallucinated ID rate, valid schema rate, reviewer actions to reach correct coverage, latency and observed cost. Record sample size, seeds and limitations. A measured improvement may be described accurately; **do not promise a gain before running**.

**Optional high-value UX feature, only after primary gates:** ask Muse for a targeted human verification question tied to fields in a verified witness's changed assignment, e.g. “Do you have an original attendee badge number to distinguish Kim from Kym?” This suggestion must be based on visibly available fields; it cannot assert the actual identity or change policy automatically.

### Security and privacy

All public fixtures use fictional records. A real-name CSV must not be transmitted to an external model without meaningful informed permission and minimization. Meta's documented **Standard mode** does not use submitted content to train its models, whereas **Contributor mode permits training use**; Standard is the default and Contributor is prohibited for genuine personal data here. Don't describe cloud Meta inference as “fully on-device” or claim security certifications.

**Prompt injection:** treat every CSV cell as hostile untrusted data. Construct strict data-only prompts; prohibit instruction following from cell text, escape UI output, and limit generated text length. A malicious registration name like “IGNORE ALL RULES” must never change system logic or permissions.

# 13 | RESEARCH EVALUATION AND THE CASE FOR NOVELTY

### Three distinct questions judges may ask

1. **Can Meta AI discover plausible aliases?** Show measured candidate recall and valid output, not a claim of infallible matching.
2. **Does JoinWitness provide an insight a standard join does not?** Show a concrete reversed conclusion under explicitly reviewed alternatives.
3. **Can that claim be trusted?** Show solver status, independent checker and tiny-case exhaustive oracle, including a deliberately invalid/tampered witness that is rejected.

### Fair comparison matrix

| Approach | What it produces | What it does not establish |
|---|---|---|
| Exact string join | Deterministic exact matching | Whether permitted nonexact links change a conclusion |
| Fuzzy best-link baseline | A proposed matching | Robustness under alternate permitted one-to-one assignments |
| Meta AI-only answer | Narrative/candidate interpretation | Valid global assignment, minimum change, or complete stability |
| **JoinWitness** | Reviewed set + valid counterexample or solver-attributed scoped stability + independent replay | Real-world identity truth or completeness of every possible candidate in reality |

**Quantitative evaluation:** Develop a seeded suite of at least **40–60 synthetic alias cases** with known ground truth for candidate triage, plus **≥100 small randomly generated admissible assignment problems** (with bounded enumeration) for exact solver/oracle parity if runtime permits. Targets are zero known critical mismatches, zero false stability certifications on enumerated cases, and zero fabricated IDs surviving validation. Report actual sample sizes, cases excluded, timeout counts, cost and model ID. This is an **internal target, not a result**.

**Best optional differentiator:** *Decision-critical review.* After a checked counterexample, identify the ambiguity whose verification matters to the conclusion and ask the user for a concrete clarifying source field. This is the strongest defensible use of AI beyond fuzzy matching, but may only ship after independent proof gates pass and honest candidate coverage is implemented. If not finished, show it as future work, not a feature.

**Claim boundaries:** no “first ever”, “guaranteed accurate”, “perfect”, “mathematically proved real-world identity”, or percentages without evidence. A mathematically proved result is always conditional on an explicit model and reviewed policy.
