## 1. Problem to fix
The current 3-attendee/4-registration flagship is a valuable, independently enumerable *proof fixture*, but is a weak **sole** demonstration of a broader decision-robustness workflow. The earlier large-number mockup was illustrative only and **not** processed data; its group arithmetic was inconsistent. It must not be reused as a verified output.

The product is **not** a generic CSV name matcher. Its approved question is: *Given the identity links a reviewer explicitly permits, can an alternative valid one-to-one assignment reverse the fixed conclusion `count(A) > count(B)`? If so, what is the minimum number of changed attendance assignments, subject to a completed solver proof and independent witness verification?*

## 2. Explicit scope correction
Original RD §04 says **high-scale data matching is OUT of V1**. Conservative standard-mode V1 caps are **100 attendance rows, 150 registration rows, up to 10 reviewed candidate links per attendance row**, with a 10-second initial interactive solver limit. Input byte limits must be read from the actual current API and remain enforced. Do **not** raise limits or advertise 48k/46k or 50k processed rows under this ticket.

We will communicate realistic usefulness using an additional **bounded synthetic demonstration**, not fake scale. Any larger enterprise-size scene must be clearly marked *future direction / conceptual illustration, not executed*. Prefer not to show hypothetical large counts on the live demo at all.

## 3. Two-layer demonstration
### A. Main showcase: practical bounded synthetic dataset (to be proven)
- Choose an actual generated dataset within V1 caps, **not** arbitrary invented values. Candidate target: 60–100 attendance records and 80–150 registrations, but only if the existing code validates those sizes and the solver genuinely runs.
- Include multiple ambiguities, shared competing candidates, genuine one-to-one conflicts, reviewed permissions, explicit unmatched policies, a valid frozen baseline, and a fixed `A > B` conclusion.
- Demonstrate that the important output is *which permitted links could change the decision*, not merely that names are similar.
- Show real counts, number of reviewed uncertain links, affected records, solver status, conditional scope, proof attribution and actual measured runtime. If performance exceeds limits or proof is unavailable, display a truthful inconclusive/timeout result, not a green claim.
- Benchmark in T10 as a **separate, non-production evaluation**. Owner-approved dataset/contract additions only after review. Never execute a costly combinatorial stress campaign uncontrolled.
- The main hero should be readable within 10–20 seconds and have one primary CTA. The data story must be visually linked from record uncertainty -> permitted alternative -> result -> independent replay.

### B. Optional tutorial / correctness exhibit: frozen 3/4 flagship
- Preserve original `T-01/T-02/T-03` and `R-A1/R-A2/R-B1/R-B2` bytes, policy, baseline, witness, digest and oracle assertions exactly.
- Keep this as the smallest teachable proof example, not the only evidence of applicability.
- Retain stable, two-change, inconclusive and incomplete-coverage demonstrations where evidence supports them.

## 4. Honest proof labels
- Solver **OPTIMAL** + checker valid: minimum can be attributed to solver; small separate oracle parity only when actually executed.
- Valid witness without optimality proof: reversal **exists**, minimum **unproven**.
- Solver-proved infeasible under reviewed set: **stable within reviewed policy**; never real-world guaranteed stable.
- Timeout/unknown/inconsistency: **inconclusive**; no stability claim.
- Unreviewed shortlist suggestions are not permissions; only explicit review choices authorise edges. Source group labels are never model-generated corrections.
- No performance values, group count changes, percentages, proof badges, or dataset-size numbers may be hardcoded as successful measured results.

## 5. Product communication / screen architecture
1. **Hero** — “Can uncertain matches change the conclusion?” Under it: “JoinWitness tests a reviewed set of possible matches and verifies whether the answer holds.” Short, plain English.
2. **Dataset context** — actual counts from parse response; clearly label *synthetic test data* and evaluation scope. Never impersonate a general 50k-row production dataset.
3. **Uncertainty explorer** — show a queue of meaningfully ambiguous records; names/IDs visible; edge types *confirmed / permitted / prohibited / not reviewed* clearly differentiated; selection is **view-only** until explicit review adoption.
4. **Decision impact** — large before/after A and B comparison driven from actual backend output; clickable changed assignments; explain *why this link matters*.
5. **Verification** — checker, solver proof attribution, receipt replay; detailed hashes/status values in optional disclosure, never the hero.
6. **Mobile** — decision and one critical record first; no data-dense 4-column table; accessible touch targets, first-Tab skip-link, reduced-motion checks.
